# おくら — 台所の在庫係エージェント コンセプトシート

作成日: 2026-11-03 / ステータス: 構想段階

> 食材も日用品も、**お蔵入りさせない**。

---

## 1. 名前

**おくら**（Okura）

- **お蔵**: 家の蔵。冷蔵庫の食材から洗剤・トイレットペーパーまで、家のストック全体を預かる存在
- **オクラ**: 冷蔵庫にいる身近な野菜
- **お蔵入り**: 「食材や日用品をお蔵入りさせない」というミッション

---

## 2. 解決する課題

- 自炊は好きだが、在庫の管理が苦手
- 残り物を組み合わせて食事を仕立てるのが苦手
- 結果として食材を腐らせる。日用品は切らしてから気づく
- AI に毎回「冷蔵庫に何があるっけ」と聞くのは面倒（自分から話しかけたくない）

## 3. コンセプト

**聞かなくても、必要なときに向こうから届く**在庫係。

- **入力はほぼ写真だけ**: レシートや買ったものを撮って送る。確認は1タップ
- **出力は通知だけ**: 朝に「今日使い切るもの＋今晩の献立」、買い物前に「買うものリスト」
- **予定を知っている**: 外食や旅行の予定を読み、献立と買い物を調整する
- **家のレシピ帳を持っている**: SNS で見つけたレシピや母のレシピを貯め、在庫に合わせてそこから提案する

### 設計の四原則
1. **判断はルール、提案は LLM**: 期限・残量・トリガー判定、レシピと在庫の突き合わせは決定的なコードで行う。LLM は候補からの選定と説明、画像やページからの抽出だけに使う
2. **料理の知識は外部化する**: 献立は登録済みのレシピと、出典付きの外部レシピから選ぶ。LLM の知識だけでレシピや分量を作らない
3. **データは指示ではない**: レシート、写真、Web ページ、SNS 投稿、カレンダーの文面はすべてデータとして扱い、指示として解釈しない
4. **永続的な変更は人が承認する**: エージェントが作るスケジュールやレシピは、ユーザーが確認するまで確定しない

---

## 4. 要件

### MVP（フェーズ0〜2）
- 在庫の登録（品名・数量・期限）。写真・レシートからの登録を含む
- 期限が近いものの一覧
- **レシピ管理**: URL・テキスト・画像（SNS のスクリーンショット、手書きのレシピ）からの登録と、登録レシピの検索
- **外部レシピの調べ物**: 食材や料理名から Web のレシピを探し、出典付きで提示。気に入ったものはそのまま登録できる
- 登録レシピと在庫の突き合わせによる今晩の献立提案
- 買い物リストの生成（不足分のみ）
- スマホから使える（外出先でも）
- 朝・夕の時刻指定通知
- 「作った」「捨てた」の1タップ記録

### v1（フェーズ3〜5）
- **カレンダーの読み取り**: 外食・旅行・会食を献立と買い物に反映
- **スケジュールの自己管理**: 時刻指定・トリガー指定のスケジュールを、エージェントが提案し、ユーザーが承認する
- **消耗品管理**: 消費ペースから「切れる日」を予測し、補充を提案

### その後（フェーズ6以降）
- 食事ログからの好みの学習
- 家族との共有
- カレンダーへの書き込み（「今晩は自炊」などの登録）
- 観測ダッシュボード

### やらないこと
- ネットスーパーや通販での自動注文
- 栄養計算の厳密化
- 外部への公開

## 5. 利用シナリオ

| タイミング | ユーザーの操作 | おくらの動き |
|---|---|---|
| 買い物帰り | レシートか買ったものを撮って送る | 品名・数量を抽出し、期限を推定して登録。「この内容で登録する？」に1タップ |
| 毎朝 | 通知を見るだけ | 「今日が期限: 豆腐・ほうれん草。今晩は味噌汁＋鶏の照り焼きはどう？」 |
| 夕方 | 「作った」を押す | 使った食材を在庫から減らし、食事ログに記録 |
| 買い物前 | 通知を見るだけ | 食材と日用品をまとめた買い物リストを、買い場所別に届ける |
| 旅行の2日前 | 何もしない | 「明後日から3日間不在。今夜と明日で葉物を使い切る献立にするね」 |
| 帰宅日 | 何もしない | 「帰宅日の夜は在庫だけで作れる簡単メニューを用意したよ」 |
| 「週末は作り置きしたい」と話す | 承認を1タップ | 「金曜 18:00 に作り置き用の買い物リストを出す」スケジュールを提案 |
| 洗剤が残り少ない | 何もしない | 「洗剤があと5日分。次のドラッグストアで買おう」 |
| SNS で作りたいレシピを見つけた | URL かスクリーンショットを共有 | 材料・分量・手順を抽出してレシピ帳に登録。「足りない材料: 生クリーム」を買い物リストに追加するか聞く |
| 実家で母のレシピを聞いた | 手書きメモの写真を送るか、聞いた内容を話す | 原文の写真を残したまま、材料と手順に整理して登録。「適量」「少々」は書き換えずにそのまま残す |
| 在庫で作れるものが登録レシピにない | 「何か探して」と頼む | Web から在庫に合うレシピを探し、出典付きで2〜3件提示。気に入ったものを1タップで登録 |
| 朝の献立提案 | 通知を見るだけ | 期限が近い食材を多く使える登録レシピを選ぶ。「お母さんの筑前煮、今ある材料で作れるよ」 |

## 6. アーキテクチャ

```
スマホ（PWA）── Tailscale ── 自宅 Mac
                               ├ Web サーバー（FastAPI）
                               ├ エージェント（自作ツールのみを使用）
                               ├ SQLite（在庫・レシピ・食材マスタ・履歴・スケジュール・実行ログ）
                               ├ レシピ取り込み（URL 取得・画像からの抽出）
                               ├ 外部レシピ検索（検索 API）
                               ├ カレンダー読み取り（読み取り専用）
                               ├ ディスパッチャ（スケジュールを評価して起動）
                               └ プッシュ通知
```

エージェントには組み込みのシェル・ファイル操作を渡さず、下記の自作ツールだけを渡す。

### ツール

| 区分 | ツール | 役割 |
|---|---|---|
| 在庫・閲覧 | `list_stock` | 在庫一覧（カテゴリで絞り込み可） |
| | `expiring_soon` | 期限が近い食材 |
| | `runout_soon` | 切れそうな消耗品（残り日数の予測つき） |
| 在庫・更新 | `add_item` | 追加（品名・数量・期限・カテゴリ） |
| | `consume_item` | 使用・廃棄・補充による増減（理由を必ず記録） |
| | `build_shopping_list` | 不足分の算出（買い場所別） |
| | `log_meal` | 作った料理の記録 |
| レシピ | `search_recipes` | 登録レシピの検索（料理名・食材・タグ・出典） |
| | `get_recipe` | レシピ詳細（人数に合わせた分量換算はコードで行う） |
| | `match_recipes_to_stock` | 在庫で作れる割合と、期限が近い食材の使用量で登録レシピを順位づけ |
| | `import_recipe` | URL・テキスト・画像からレシピを抽出し、確認待ちで保存 |
| | `web_search_recipes` | 外部レシピの検索（出典 URL つきで返す） |
| | `update_recipe` | メモ・タグ・評価の更新 |
| 予定 | `get_calendar_events` | 指定期間の予定（タイトルと日時のみ） |
| スケジュール | `create_schedule` | 登録（承認待ちで保存） |
| | `list_schedules` | 一覧と直近の実行結果 |
| | `update_schedule` | 時刻・条件・プロンプト・有効/無効の変更（承認制） |
| | `delete_schedule` | 削除 |

スケジュールごとに許可ツールを絞る。例: 朝の通知は「在庫・閲覧」と「予定」のみ。

### データモデル（SQLite）

- `items`: id, category（food / consumable）, name, quantity, unit, expires_on（NULL 可）, location（冷蔵・冷凍・常温・日用品棚）, status, added_on
  - 消耗品用（NULL 可）: reorder_point, lead_time_days, buy_at（スーパー / ドラッグストア / 通販）, opened_on
- `stock_events`: id, item_id, kind（add / consume / discard / restock / adjust）, delta, at, source（photo / receipt / tap / agent / stocktake）
  - 消費ペースと廃棄回数は、このテーブルから集計して求める
- `recipes`: id, title, source_type（sns / web / family / self）, source_url, source_label（例: 母、投稿者名）, servings, steps, tags, notes（コツ・アレンジ）, original_attachment（元のスクリーンショットや手書きの写真）, confirmed, times_cooked, last_cooked_on, rating
- `recipe_ingredients`: recipe_id, ingredient_id, raw_text（原文の表記）, quantity（NULL 可）, unit, optional
  - 「適量」「少々」などは quantity を NULL にし、raw_text をそのまま残す
- `ingredients`（食材マスタ）: id, name, aliases（「豚こま」「豚小間切れ」など表記ゆれ）, storage（冷蔵・冷凍・常温）, shelf_life_days, substitutes
  - 在庫とレシピの突き合わせ、期限の推定に使う。保存日数は出典を記録し、ユーザーが修正できる
- `meals`: id, date, title, recipe_id（NULL 可）, used_items, suggested_by_agent, rating
- `schedules`: id, name, kind（time / trigger）, cron または run_at, trigger_spec（JSON）, prompt, allowed_tools, cooldown, created_by（user / agent）, approved, enabled, last_run_at
- `runs`: id, schedule_id, started_at, status, model, prompt_hash, tokens, cost, output, notified
  - model と prompt_hash は、評価結果と実行を比較できるようにするため（`docs/evals.md` §3）
- `tool_calls`: エージェントの全ツール呼び出しログ

category と `stock_events` はフェーズ0から持たせ、消耗品への拡張時に作り直さずに済むようにする。

### レシピ管理と料理知識の外部化

料理の知識は、LLM の中ではなく「レシピ帳」「食材マスタ」「出典付きの外部検索」の3つに置く。

**登録**
- **SNS・Web**: URL を共有すると、ページを取得して材料・分量・手順を抽出する。ログインが必要な投稿や動画レシピは、スクリーンショットかキャプションのコピーで登録する
- **家族のレシピ**: 手書きメモの写真、または聞いた内容のテキスト・音声から登録する。原文（写真・文面）を必ず残す
- **抽出結果は確認してから確定**: 抽出したレシピは `confirmed = false` で保存し、ユーザーが1タップで確定する。読み取れなかった箇所は空欄のまま示し、推測で埋めない

**提案**
- 献立提案は、`match_recipes_to_stock` がルールで順位づけした登録レシピの上位候補から選ぶ
- 登録レシピに合うものがないときだけ、外部検索の結果を出典付きで提示する。外部レシピは登録されるまで「候補」として扱う
- 分量の人数換算、使う食材の在庫からの差し引きはコードで行う
- LLM に任せるのは、候補からの選定、選んだ理由の説明、登録時の抽出だけ

**調べ物**
- 「ほうれん草と豆腐で何か」「筑前煮の作り方」など、食材や料理名から外部レシピを探す
- 結果には必ず出典 URL を付ける。出典のない作り方や分量は示さない

### カレンダー連携
- 読み取り専用
- 「外食」「会食」「旅行」「出張」などのキーワード、または専用カレンダーで「その食事は自炊しない」を判定する。曖昧な予定は推測せず、通知で一言確認する
- LLM に渡すのはタイトルと日時だけ。参加者・場所・メモは渡さない

### スケジュール管理

**2種類のスケジュール**
- **時刻指定**: cron 式または1回限りの日時（毎朝 7:00、金曜 18:00 など）
- **トリガー指定**: 条件を満たしたら起動。条件は JSON で書き、ルールで判定する（LLM は使わない）
  - 食材の期限が N 日以内になった
  - 消耗品の残り日数が N 日を下回った（`runout_within_days <= 5`）
  - 「旅行」を含む予定が追加された／N 日前になった
  - 在庫が登録・更新された

各スケジュールは、起動時プロンプト、許可ツール、cooldown（同じトリガーで連続通知しない間隔）、実行履歴を持つ。

**暴走・悪用の防止**
- エージェントが作ったスケジュールは、ユーザーが承認するまで有効にしない（`approved = false` で保存）。承認は通知から1タップで行う
- スケジュール数の上限、最短実行間隔、1日あたりの実行回数とコストの上限を設ける
- スケジュール実行中のエージェントには `create_schedule` を渡さない（連鎖的な増殖の防止）
- 外部データ（カレンダー、レシート画像）を読む実行には、スケジュール系ツールを渡さない

### 消耗品管理
食材は「期限」で、消耗品は「**消費ペース**」で管理する。

- **対象**: トイレットペーパー、洗剤、シャンプー、ゴミ袋、電池、ティッシュなど
- **予測**: `stock_events` の補充・開封の間隔から消費ペースを推定し、「あと何日で切れるか」を出す
- **補充の判定**: 残り日数が「リードタイム＋余裕」を下回ったら買い物リストに入れる
- **カレンダーとの連携**: 来客の前は補充を前倒しし、長期不在の前は補充提案を止める
- **入力**: 補充時の写真・レシート、または「使い切った」の1タップ
- **買い物リスト**: 食材と消耗品を1つにまとめ、買い場所別に分ける

## 7. セキュリティ

- Tailscale 内のみで公開（Funnel は使わない）。ACL でアクセス元の端末を絞る
- アプリ側にも簡易認証を付ける
- API キーは Mac 上で管理し、スマホ側には出さない
- エージェントにシェル実行権限を与えない（画像内の指示によるプロンプトインジェクション対策）
- カレンダーは読み取り専用。外部サービスの認証情報は Mac 内に閉じる
- URL の取得は、ユーザーが送った URL と、検索結果として返ってきた URL に限る。ページ内のリンクを自動でたどらない
- 外部ページを読んだ実行では、在庫の更新系ツールとスケジュール系ツールを渡さない。レシピは確認待ちでのみ保存する
- 外部検索・URL 取得は、ユーザーとの対話中だけ使う。スケジュール起動の実行では、登録済みのレシピだけを使う
- スケジュールの登録・変更は承認制
- 各アカウントの 2FA を必須にする

## 8. 運用

- **棚卸し**: 週1回、おくらから棚卸しの通知を出し、在庫と実物のズレを直す
- **コスト上限**: 1日あたりの上限を超えたら、LLM を使う提案を止め、ルールベースの通知だけにする

## 9. 自作で得られる学び

- ツール設計とエージェントループの設計
- 能動的（スケジュール起動型）エージェントの実装

## 10. ロードマップ

| フェーズ | 内容 | 完了の定義 | 目安 |
|---|---|---|---|
| 0 | SQLite と CLI で手入力、`expiring_soon` が動く。食材マスタの初期データ | 1週間、手入力で在庫を回せる | 1週末 |
| 1 | PWA と Tailscale 経由のスマホ利用、レシピ登録（URL・テキスト）、在庫との突き合わせによる献立提案、外部レシピ検索、「作った/捨てた」記録 | 外出先から在庫を見て、登録レシピから献立を受け取れる | 2週末 |
| 2 | 写真・レシート登録、画像からのレシピ登録（スクリーンショット・手書き）、ディスパッチャ、朝夕の通知 | 写真から在庫とレシピを登録でき、通知が毎日届く | 2週末 |
| 3 | カレンダー読み取り（不在日の判定、献立・買い物への反映） | 旅行前に使い切り献立が届く | 1〜2週末 |
| 4 | トリガー指定スケジュール、エージェントによる提案と承認 UI | 通知から1タップで承認できる | 2週末 |
| 5 | 消耗品管理（消費ペース推定、補充提案、買い場所別リスト） | 日用品の補充提案が届く | 1〜2週末 |
| 6 | 好みの学習、観測ダッシュボード、家族共有 | — | 随時 |

フェーズ1以降は、表の「完了の定義」に加えて、そのフェーズまでに着手したエージェント評価の項目がすべて合格基準を満たすことを完了の条件とする（`docs/evals.md` §1・§2）。

## 11. 成功指標

| 指標 | 測り方 |
|---|---|
| 食材の廃棄回数（週あたり） | `stock_events` の discard 件数 |
| 登録の手間（1回あたり） | 写真送信から確定までの秒数 |
| 献立の採用率 | 提案のうち `log_meal` に記録された割合 |
| レシピ帳の活用度 | 作った料理のうち、登録レシピから作った割合 |
| レシピ登録の手間 | 共有から確定までの秒数と、手直しした項目の数 |
| 通知の開封率 | 通知のタップ数／送信数 |
| 日用品の欠品回数（月あたり） | 「切らした」記録の件数 |
