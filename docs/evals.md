# おくら — エージェント評価（Evals）

> **状態: 下書き。** 骨組みと論点だけを置いている。各節の「未決」を埋めて確定させる。

`docs/concept.md` が「何を作るか」の正典であるのに対し、この文書は「エージェントが正しく振る舞っていることを、出荷前にどう確かめるか」を定める。運用中の成功指標（`concept.md` §11）は実際に使ったあとの結果を測るもので、この文書が扱う出荷前の評価とは別物である。

---

## 1. 目的と範囲

- 評価の対象は、LLM が関わる振る舞い（候補からの選定と説明、画像やページからの抽出、ツール呼び出しの順序と範囲）
- 決定的なコード（期限・残量・トリガー判定、レシピと在庫の突き合わせ、スケジュールごとの許可ツールの強制）は対象外。これらは `tests/` のユニットテストで確かめる
- 未決: 評価をフェーズごとの「完了の定義」（`concept.md` §10）に含めるか

## 2. 評価項目

設計の四原則（`concept.md` §3）を、合否を判定できる形に落とす。

| 原則 | 評価項目 | 判定方法 | 着手フェーズ |
|---|---|---|---|
| 1. 判断はルール、提案は LLM | 抽出の精度（レシート → 品目・数量・日付、レシピ画像 → 材料・手順） | 正解付きのサンプル集と項目ごとに照合する | 1〜2 |
| 1. 同上 | 提案理由の説明が在庫や期限の事実と矛盾しない | LLM による採点（ルーブリックは未決） | 1 |
| 2. 料理の知識は外部化する | 提案したレシピが、渡した候補の中にある | ツール呼び出しの記録・出力を機械的に検査する | 1 |
| 3. データは指示ではない | 指示文を埋め込んだレシート・Web ページ・カレンダーを読ませても、許可されていないツールが呼ばれない | ツール呼び出しの記録を機械的に検査する | 1〜3 |
| 4. 永続的な変更は人が承認する | 承認なしに確定系のツールが呼ばれない | ツール呼び出しの記録を機械的に検査する | 1, 4 |

- 未決: 各項目の合格基準（例: 抽出の正答率の閾値、プロンプトインジェクションは 0 件を必須とするか）

## 3. 評価できるようにするための設計要件

エージェントのループを書く前に決めておかないと、あとから直しにくい部分。

- LLM の呼び出しは1つのインターフェースを通す。応答を記録し、記録した応答を再生して実行できるようにする（決定的な回帰テストとコストの抑制のため）
- すべてのツール呼び出しを `tool_calls` に記録する（`concept.md` §6 のデータモデル）。評価はこの記録に対して判定する
- 未決: モデル名・プロンプトの版を実行記録に残す方法（評価結果を比較できるようにするため）
- 未決: この節を ADR として記録するか

## 4. 評価データ

- リポジトリにコミットするのは、作った例（架空のレシート・ページ・予定）だけにする
- 実際のレシート写真やカレンダーは個人情報を含むので、git の管理外に置く
- 未決: 実データの置き場所と、作った例を増やす手順

## 5. 実行方法

- 実際に API を呼ぶ評価は `make check` に含めない（コストと結果の揺らぎのため）。`make eval` を別に用意する
- 記録した応答を再生する評価は、決定的に実行できるので `make check` / CI に含めてよい
- 未決: 置き場所（`evals/` を想定）、既製のフレームワークを使うか自作するか、結果の保存と比較の方法

## 6. 見直す条件

- 評価1回あたりのコストが、1日のコスト上限（`concept.md` §8）を圧迫する
- 同じ入力でも実行ごとに合否が変わり、結果が安定しない

いずれかが起きたら、記録した応答を再生する評価を中心に寄せる。
